0. 执行模式

你现在运行在 Goal 模式。

你的目标不是继续分析、提出建议或只生成审计报告，而是：

在完整读取 v1.9.0 PDF、LaTeX 源码、全量审校与重构方案、全书审计工作簿和版式参考讲义之后，直接修改 LaTeX 源码，完成全书内容、前置概念、数学推导、例题解答、绘图、字体、颜色和版式的系统重构，编译并交付《统计学习方法初学者讲义·合并总册 v2.0.0》。

除非出现“源代码确实缺失且无法恢复”或“本机不存在任何可用 LaTeX 工具链且已完成替代方案排查”这两类不可恢复阻断，否则不得停留在计划、局部修改、审计或中间报告阶段。

不得把“已列出待办”“已完成部分章节”“已给出建议”描述成完成。只有最终 PDF、完整 LaTeX 源码、质量报告和交付清单均实际存在，且关键质控门通过，任务才算完成。

0.1 最高优先级：禁止过度审计、重复质检与无休止回查

本节高于后文所有笼统的“再次扫描、全面复核、逐页审查”表述。审计只服务于实际修改和验收；已有问题、源码位置、修改动作和验收标准足够时，必须立即进入实施。

Codex 的最终目标是实际完成 v2.0.0 LaTeX 源码修改、绘图重制、例题解答重写、前置概念补充、排版优化和最终 PDF 编译，而不是生成最多的审计材料。

把现有 110 条问题、99 幅图、1234 个例题/练习/解析标记、68 个算法和逐页风险条目映射到源码；

后续全书检查只能是：

针对已经实施修改的验收
编译回归
链接回归
视觉回归
数学定向测试

不得重新从零建立问题清单。

B.2 每章最多两轮内容审查

每章允许：

“为了更保险”“可能还有问题”“换一个 Agent 再看看”不构成重新审查理由。

3. 是否存在具体失败证据？

若前两项为“是”、第三项为“否”，立即进入下一阶段。

E. 编译、渲染和像素比较次数限制

2. 门 A
3. 门 B
4. 门 C
5. 门 D

编辑过程中使用：

若某个质控门失败，可在修复后重新运行该门，但必须记录具体失败原因；不得把每次普通编辑都包装为质控门失败。

门 C：图形、例题和版式基本完成后

前置结构变化页
P0/P1 数学修复页
对应高风险页
发生版式变化的目标页

禁止在内容尚未稳定时多次渲染全部 705 页。

E.3 像素差异比较

全书级像素差异比较只在门 D 执行一次。

普通修改只比较目标页面，不得反复对全书执行像素 diff。

G. Subagent 防止重复审计

同时开启 Subagent 最多 3 个。

Subagent 不得再创建嵌套 Subagent。

一个章节只允许一个内容负责人。

一幅图只允许一个绘图负责人。

同一个 .tex、.sty、.tikz 或数据文件不得由两个 Agent 同时编辑。

Subagent 的主要工作必须是修改，不得长期只读审计。

禁止三个 Agent 对同一公式、同一例题或同一页面分别审查，再由主线程投票。

只有以下对象允许第二人复核：

14 条 P0；

首次修复未通过测试的问题；

存在两个来源直接冲突的问题；

主线程已经找到具体数学反例的问题。

QA Agent 只检查合并后的结果和失败项，不得重新从头审计全书。

Subagent 完成 handoff 后必须关闭或转换任务，不得常驻并重复扫描。

H. 问题关闭后不得无证据重开

问题标记为“已关闭”后，只有出现以下新证据才允许重开：

编译错误
数学测试失败
明确反例
链接失效
页面重叠、裁切、乱码或黑块
符号冲突
编号冲突

重开时必须记录：

失败证据
受影响文件
受影响页面
修复动作
再次验收结果

禁止以主观怀疑重开问题。

I. 最小充分验收证据

普通问题关闭通常只需要：

1. 源码差异或提交编号；
2. 一项针对性检查；
3. 视觉问题再附一张目标页面渲染。

不得要求：

同一页面多轮重复截图
同一公式三名 Agent 交叉确认
普通文字修改计算哈希
每个小改动生成独立报告
每个章节生成完整审计工作簿

视觉问题一般使用：

一张 100% 页面图
必要时一张局部放大图
一张灰度检查

即构成充分证据。

J. 工作量比例约束

按实际工作量控制：

输入发现、规划和审计：不超过约 15%
实际源码修改、重写、重绘和排版：不少于约 70%
最终回归、构建和交付：约 15%

该比例按文件修改、重绘和构建工作量判断，不要求伪造精确 token 数据。

若发现：

审计报告数量持续增加
实际修改文件很少
Subagent长期只读不改
全书扫描次数不断增加

主线程必须立即停止非必要审计并转入实施。

L. 覆盖原提示词中容易引发过度审计的表述

原主提示词中出现“全部扫描”“逐页审查”“完整复核”时，统一解释为：

首次使用现有报告和工作簿完成一次定位；
修改后按既定验收标准进行一次回归；
不得从零重复发现问题型审计。

“全书逐页视觉检查”统一解释为：

门 C 和门 D 各执行一次全书渲染；
高风险页与修改页人工检查；
其余页采用自动扫描和分批复核；
不得在每个阶段重复逐页检查。

“所有例题和算法复核”统一解释为：

以现有审计清单为索引完成一次正确性核验；
核心和高风险对象实际重写；
普通对象通过单次规范化与定向验收；
不得反复重审同一对象。

M. 完成判定新增条款

只有满足这些条件，才可宣布任务完成。

3. 不可破坏的全书原则

保留五册、37 章和核心知识覆盖。

除用户明确要求删除的内容外，不得无理由删除知识点。

高级但正确的内容可移入“进阶选读”或附录，不得伪装成初学主线。

定义必须先于实质使用；直觉必须先于最一般形式。

数学主线优先于工程状态码。

图必须帮助理解正文，不得只做装饰。

例题解答必须教会读者如何找到第一步，而不只是给答案。

复杂页面通过拆页、重组和移附录解决，不通过整体缩小字号解决。

全书符号、样本方向、随机矩阵方向、状态码和术语必须统一。

新增文字必须服务于知识依赖，不得用模板机械膨胀页数。

4. Subagent 使用约束

4.1 数量上限

同时开启的 Subagent 最多 3 个。

不允许 Subagent 再创建嵌套 Subagent。

简单搜索、路径确认、单文件替换和编译检查不得新开 Subagent。

主线程是唯一最终合并者和最终交付责任人。

4.2 第一轮分工

Subagent A：基础与前置概念

负责：

前置页
第1—11章
前置概念依赖矩阵
概念首次出现审计
概念桥改写
基础符号与依赖顺序

Subagent B：监督学习与序列模型

负责：

第12—23章
数学推导核验
核心例题与练习解析
算法数学层重写

Subagent C：无监督、采样、主题模型与图排序

负责：

第24—37章
数学推导核验
核心例题与练习解析
算法数学层重写

4.3 第二轮角色转换

第一轮完成并由主线程合并后，关闭原任务，再顺序复用三个 Agent 槽位：

Agent A：图 1—23 的绘图重制与图文核对；

Agent B：图 24—37 的绘图重制与图文核对；

Agent C：逐页视觉 QA、链接、索引和构建复核。

任何时刻不得超过 3 个 Subagent。

4.4 文件所有权

同一 .tex、.sty、.tikz 或数据文件不得由两个 Agent 同时编辑。

每个 Agent 必须使用独立工作树、独立分支或独立临时目录。

Agent 完成后必须提交：

logs\subagent_<id>_handoff.md

内容包括：

修改文件
解决的问题 ID
新增概念桥
重写例题
重绘图
运行的测试
仍需主线程决策的事项

主线程只能依据补丁、提交和 handoff 合并，不得依赖聊天记忆猜测修改内容。

4.5 自动上下文压缩、会话恢复与背景信息防丢失协议

本节是长期任务的强制可恢复协议。Codex 可能在会话接近上下文窗口限制时自动压缩历史；因此，聊天记录只能作为临时缓存，仓库文件、Git 提交、问题台账和状态文件才是事实来源。任何重要背景、决定、进度、失败原因和下一步动作都不得只存在于聊天或模型内部记忆中。

本协议同时适用于：

自动上下文压缩
手动压缩
Codex resume
IDE/CLI重连
主线程暂时中断
Subagent结束与重新分配
电脑重启后的续作

上下文压缩不是新的审计、哈希或质控门，不得因此重新扫描全书、重新编译全书或重新建立问题清单。

4.5.1 上下文保存的事实优先级

压缩后若摘要、聊天记忆和磁盘状态不一致，按以下顺序确定事实：

当前用户提示词与仓库中的主提示词副本；

Git 当前分支、HEAD、工作区实际差异和已存在文件；

qa\context\CURRENT_STATE.yaml；

唯一问题关闭台账、概念矩阵、绘图矩阵和例题矩阵；

qa\context\DECISIONS.md；

Subagent 的补丁、提交和 handoff；

自动压缩生成的会话摘要；

模型对先前聊天的模糊记忆。

不得用压缩后的聊天摘要覆盖磁盘上的更新结果。若状态文件与 Git 不一致，先核对差异，再修正状态文件；不得凭摘要猜测并覆盖源码。

4.5.2 阶段 0 必须建立的持久化上下文目录

在 Git 根目录创建：

AGENTS.md
.codex\
├─ hooks.json
└─ hooks\
   ├─ pre_compact_checkpoint.py
   └─ context_rehydrate.py
qa\context\
├─ PROJECT_CHARTER.md
├─ PROMPT_INDEX.md
├─ CURRENT_STATE.yaml
├─ ACTIVE_PACKET.md
├─ NEXT_ACTIONS.md
├─ DECISIONS.md
├─ FILE_OWNERSHIP.csv
├─ COMPACTION_LOG.csv
├─ RECOVERY_LOG.md
└─ snapshots\

这些文件属于恢复基础设施，不得散落在聊天中，也不得删除到 build 临时目录。

PROJECT_CHARTER.md

只记录长期不变的项目事实：

最终目标与目标读者
ROOT与唯一写入目录
五册37章不可破坏原则
删除入门诊断和参考资料
符号索引位置
P0/P1/P2处理要求
绘图、例题、概念桥和排版硬门槛
Subagent并发上限
哈希H0/H1/H2
质控门A/B/C/D
禁止过度审计
最终交付物

不得记录频繁变化的当前任务。文件建议控制在 4000—7000 中文字以内。

PROMPT_INDEX.md

保存完整主提示词在仓库中的路径，并按阶段建立标题索引：

阶段/主题
主提示词标题
文件路径
相关问题台账/工作表
必须读取的最小范围

完整主提示词复制到：

manifests\MASTER_PROMPT_v2.0.0.md

不得把整个超长主提示词复制到 AGENTS.md 或每次恢复上下文中。恢复时只按 PROMPT_INDEX.md 读取当前阶段相关部分。

CURRENT_STATE.yaml

该文件是主线程的唯一机器可读进度状态，必须保持短小、明确、无散文。推荐结构：

schema_version: 1
project: statlearn-v2.0.0
last_updated_utc: ""
phase: ""
quality_gate: "none"
active_owner: "main"
active_issue_ids: []
active_chapters: []
active_files: []
locked_files: []
current_goal: ""
last_completed_action: ""
next_exact_action: ""
acceptance_criteria: []
tests_passed: []
tests_pending: []
blockers: []
open_decision_ids: []
relevant_handoff_files: []
git:
  branch: ""
  head: ""
  dirty_paths: []
  stash_refs: []
last_full_build: ""
last_target_build: ""

硬性要求：

next_exact_action 必须是一个可以立即执行的具体动作，不能只写“继续修改”；

只列当前任务涉及的 issue、章节和文件，不能把 110 条问题全部复制进来；

每次结构决策、文件所有权变化、阶段切换和原子提交后更新；

文件建议不超过 200 行或 12 KB；

更新采用原子写入：先写临时文件，再替换正式文件，避免半写状态。

ACTIVE_PACKET.md

这是压缩后直接注入模型的精简上下文包，建议控制在 1800—3500 tokens，最多不得超过 4500 tokens。固定包含：

1. 当前目标
2. 当前阶段与质控门
3. 活跃问题ID
4. 当前修改文件与文件所有者
5. 已完成动作
6. 已通过测试
7. 尚待执行的精确下一步
8. 当前阻断
9. 最近必须遵守的决策ID
10. 禁止事项：不得重审、不得重新基线、不得覆盖他人文件

不得把整份审校报告、工作簿、编译日志或巨大 diff 塞入该文件。大型证据只保留路径和定位锚点。

DECISIONS.md

使用追加式决策日志，禁止重写历史。每项格式：

DEC-0001
时间：
问题/范围：
决定：
理由：
拒绝的替代方案：
影响文件：
来源/证据：
是否可逆：

以下决定必须立即记录，而不能等到阶段末：

章节移动
数学公式口径选择
符号/样本方向统一
算法状态语义
图的拆分/删除/重绘
例题保留/压缩/重写
字体和版式全局变更
工作簿条目“保留并说明”

NEXT_ACTIONS.md

只保留按顺序排列的 3—7 个下一步动作。每项写：

动作
涉及文件
问题ID
完成条件
预计使用的局部测试

禁止写几十项长期愿望清单；长期任务仍由唯一问题台账管理。

FILE_OWNERSHIP.csv

字段：

path,owner,branch,issue_ids,status,last_update_utc

主线程和 Subagent 在读写前都必须核对。上下文压缩后不得根据聊天印象重新分配文件。

4.5.3 AGENTS.md 的使用规则

在仓库根目录建立精简的 AGENTS.md，用于每次启动、恢复和新 Agent 进入项目时加载不变量。它必须：

指向 manifests\MASTER_PROMPT_v2.0.0.md；

指向 qa\context\PROJECT_CHARTER.md、CURRENT_STATE.yaml、ACTIVE_PACKET.md；

声明 Git、磁盘状态和唯一台账高于聊天摘要；

声明压缩后先恢复再修改；

声明禁止过度审计、禁止重复全书扫描；

声明同一文件不能被两个 Agent 同时编辑；

声明每次完成原子任务必须更新状态文件和提交；

保持简短，只保存高频、稳定规则。

不得把 1900 行主提示词全文复制进 AGENTS.md。如需目录级特殊规则，可在对应目录使用更近的 AGENTS.md 或 AGENTS.override.md，但必须避免相互冲突。

4.5.4 日常写入纪律：先落盘，再依赖

为了使自动压缩发生在任意时刻时仍可恢复，Codex 必须遵守：

超过 3 步的任务，执行前先把步骤写入 NEXT_ACTIONS.md；

产生重要数学或架构决定后，立即写 DECISIONS.md；

读取长工作簿、PDF、日志或工具输出后，把真正影响修改的结论写入台账或状态文件，不能只留在终端输出和聊天中；

修改多个文件前，先把文件列表写入 CURRENT_STATE.yaml 和 FILE_OWNERSHIP.csv；

完成一个可独立验收的原子单元后：

运行局部测试；

更新问题台账；

更新 CURRENT_STATE.yaml、ACTIVE_PACKET.md 和 NEXT_ACTIONS.md；

创建 Git 提交；

在以下高上下文消耗动作之前先更新一次状态：

读取长篇报告或大量 PDF 页面；

运行全书或分册编译；

查看超长编译日志；

生成/比较大规模 diff；

启动或关闭 Subagent；

切换阶段、工作树或分支；

不要求每次改单字都更新状态，避免形成新的流程负担；状态更新以“原子任务、关键决定、高上下文动作”为单位。

4.5.5 Git 原子提交与脏工作区保护

每个提交只解决一组高度相关的问题，提交信息至少含：

阶段
章节/文件
问题ID
修改类型

示例：

phase-B/ch22: fix CRF terminal factor [ISS-065]
phase-C/fig32: split MH workflow and diagnostics [FIG-32.2, FIG-32.7]

自动压缩时允许工作区存在未提交修改，但必须由恢复脚本保存：

git status --short
git diff --stat
git diff --binary
当前分支与HEAD
最近10个提交

快照写入：

qa\context\snapshots\<UTC时间戳>\

不得为了压缩而自动提交未经测试的代码，也不得自动 git reset --hard、自动丢弃修改或自动清空 stash。

4.5.6 自动压缩 Hook：优先实现，失败时采用手动回退

若当前 Codex CLI/IDE 支持项目级 Hooks，阶段 0 必须建立并验证 .codex\hooks.json。

推荐配置逻辑：

{
  "description": "Preserve and rehydrate the v2.0.0 textbook task across compaction.",
  "hooks": {
    "PreCompact": [
      {
        "matcher": "^(auto|manual)$",
        "hooks": [
          {
            "type": "command",
            "command": "python3 \"$(git rev-parse --show-toplevel)/.codex/hooks/pre_compact_checkpoint.py\"",
            "commandWindows": "powershell -NoProfile -ExecutionPolicy Bypass -Command \"$r=(git rev-parse --show-toplevel); py -3 (Join-Path $r '.codex/hooks/pre_compact_checkpoint.py')\"",
            "timeout": 30,
            "statusMessage": "Saving compaction-safe project state"
          }
        ]
      }
    ],
    "SessionStart": [
      {
        "matcher": "^(compact|resume|startup)$",
        "hooks": [
          {
            "type": "command",
            "command": "python3 \"$(git rev-parse --show-toplevel)/.codex/hooks/context_rehydrate.py\"",
            "commandWindows": "powershell -NoProfile -ExecutionPolicy Bypass -Command \"$r=(git rev-parse --show-toplevel); py -3 (Join-Path $r '.codex/hooks/context_rehydrate.py')\"",
            "timeout": 30,
            "statusMessage": "Restoring compacted project context",
            "additionalContextLimit": 4500
          }
        ]
      }
    ]
  }
}

Codex 必须按当前安装版本的实际 Hook 语法核对并修正上述示例，不能盲目复制后假装启用。完成后使用 /hooks 或当前版本等价命令检查来源、信任并做一次无破坏测试。

禁止：

使用 PreCompact 阻止正常自动压缩；

在 Hook 中运行全书审计、全书编译、哈希或网络研究；

将 additionalContextLimit 设为 0 并无上限输出；

把完整工作簿、完整 prompt 或秘密写入 Hook 输出；

依赖未承诺稳定的会话 transcript 格式解析关键状态。

若当前 Codex 表面不支持 Hooks、项目不受信任或 Hook 无法启用：

记录到 qa\context\RECOVERY_LOG.md；

不得因此停止主任务；

使用本节的手动恢复协议；

仍必须维护所有状态文件和 Git 原子提交。

4.5.7 pre_compact_checkpoint.py 的最小职责

脚本必须是确定性的，只做本地快速保存：

从 Hook stdin 读取 session_id、turn_id、trigger、cwd；

定位 Git 根目录；

读取但不修改当前源码；

保存 Git 分支、HEAD、状态、diff stat 和 binary diff；

复制 CURRENT_STATE.yaml、ACTIVE_PACKET.md、NEXT_ACTIONS.md、FILE_OWNERSHIP.csv；

复制最近相关 handoff 的路径列表，不复制整个聊天；

追加 COMPACTION_LOG.csv；

成功后退出 0，不向模型输出大量文本；

失败时写 RECOVERY_LOG.md 和 stderr，但不得删除或覆盖工作区。

该脚本不得尝试从聊天 transcript 推断未落盘的数学决定。未落盘决定视为流程缺陷，压缩后由有限范围恢复处理。

4.5.8 context_rehydrate.py 的最小职责

脚本读取：

AGENTS.md
PROJECT_CHARTER.md
CURRENT_STATE.yaml
ACTIVE_PACKET.md
NEXT_ACTIONS.md
DECISIONS.md中最近相关条目
FILE_OWNERSHIP.csv中活跃记录
Git branch/HEAD/status
最近相关handoff

然后向 Codex 返回一个简洁的 SessionStart.additionalContext，内容顺序固定为：

[不可变目标与禁止事项]
[当前阶段、活跃问题和文件]
[Git分支、HEAD与脏文件]
[已完成动作和测试]
[精确下一步]
[阻断和待决策]
[必须读取的磁盘文件路径]
[恢复后禁止重新执行的步骤]

若输出过长，优先保留：

当前目标
问题ID
文件
精确下一步
Git状态
阻断
不可变约束

删除历史叙事和已关闭任务详情。不得返回秘密或完整日志。

4.5.9 自动压缩后的强制恢复顺序

检测到 SessionStart source=compact、压缩后续写、resume 或明显背景缺失时，Codex 在继续编辑前必须依次执行：

读取根目录 AGENTS.md；

读取 qa\context\CURRENT_STATE.yaml；

读取 qa\context\ACTIVE_PACKET.md 和 NEXT_ACTIONS.md；

运行 git branch --show-current、git rev-parse HEAD、git status --short；

核对 FILE_OWNERSHIP.csv；

读取当前活跃 issue 在唯一问题关闭台账中的行；

读取当前阶段在 PROMPT_INDEX.md 指向的主提示词小节；

有 Subagent 时读取对应 handoff；

将磁盘状态与压缩摘要比较；

更新一次 CURRENT_STATE.yaml 的恢复时间与核对结果；

从 next_exact_action 继续。

恢复时禁止：

重新读取全部705页PDF
重新完整读取所有工作簿
重新运行阶段0
重新建立问题台账
重新分配全部Subagent
重新执行已经通过的质控门
因为“不确定”而从本章第一页开始重做

4.5.10 三档恢复判定

绿色恢复

满足：

CURRENT_STATE中的branch/HEAD与Git一致
活跃文件存在
文件所有权一致
状态中的下一步仍未完成

操作：直接继续 next_exact_action。

黄色恢复

出现：

工作区有状态文件未列出的脏文件
最近提交比状态文件更新
Subagent handoff已到达但尚未合并
局部测试结果未登记

操作：只检查 Git diff、最近提交和活跃 issue，修正状态后继续。不得扩展为全书审计。

红色恢复

出现：

分支或HEAD严重不一致
CURRENT_STATE缺失/损坏
活跃文件被其他Agent覆盖
存在无法解释的大规模未提交修改
问题台账与源码状态矛盾

操作：暂停新编辑；基于 Git、快照和 handoff 进行有限恢复，生成：

qa\context\RECOVERY_<UTC时间戳>.md

只恢复当前阶段和活跃文件；除非证据表明基线整体损坏，不得重跑全书发现型审计。

4.5.11 Subagent 的压缩安全协议

每个 Subagent 启动时必须获得一个独立的、范围受限的任务包，包含：

负责问题ID
允许编辑文件
禁止编辑文件
权威来源路径
预期输出
局部测试
handoff模板

Subagent 不得依赖主线程聊天历史。若 Subagent 自身发生压缩或恢复，必须读取它的任务包、分支状态和最近 handoff 草稿。

Subagent 每完成一个原子任务，就更新自己的：

logs\subagent_<id>_handoff.md

主线程在压缩后只按补丁、提交、任务包和 handoff 合并，不根据“我记得 Agent 已经做过”判断。

4.5.12 配置自动压缩阈值的原则

不得为了避免压缩而盲目把自动压缩阈值调到接近模型上下文上限。默认值由当前模型和 Codex 版本管理时，优先保留默认值。

若用户或环境已经配置：

model_auto_compact_token_limit
model_auto_compact_token_limit_scope

则：

在 manifests\codex_runtime.md 记录实际值；

核对不超过当前模型可用上下文；

为工具输出和恢复上下文保留余量；

不通过频繁改变阈值代替状态落盘；

未经用户要求不得修改全局 ~/.codex/config.toml；优先使用项目级配置，并在项目受信任时生效。

Codex Memories 可作为补充，但不得作为当前分支、问题状态、数学决定和文件所有权的唯一来源。

4.5.13 上下文包的压缩与信息保留规则

恢复摘要必须优先保留“约束、决定、状态、下一步”，压缩或丢弃“重复叙述、已关闭历史和原始长输出”。优先级：

P0/P1数学决定
用户明确要求
不可破坏原则
当前活跃问题与验收标准
当前文件、分支、HEAD和所有权
下一精确动作
已通过测试及不能重跑的阶段
阻断和待决策
最近相关提交
历史说明与重复证据

不得把以下不同状态合并成模糊表达：

已修改 ≠ 已测试
已测试 ≠ 已关闭
数值停止 ≠ 数学收敛
已生成图源 ≠ 已编译进最终PDF
Subagent完成 ≠ 主线程已合并
门C通过 ≠ 门D通过
